# Status codes and error bodies

Each status code has exactly one meaning across the whole API. Clients (the web app, scripts, other teams) branch on the code: 401 signs the user out, 403 shows "you can't do that", 404 shows the not-found page, 422 shows a form error, 429/503 back off and retry. If one code means two things, one of those client branches does the wrong thing.

## The error body

```json
{"error": "Current password is incorrect.", "field": "currentPassword"}
```

| Key | Rule |
| - | - |
| `error` | Always present. A short sentence a user can read and act on. Generic about internals: never SQL, exception text, file paths, upstream responses or "row not found in table X". |
| `field` | Present only when exactly one input field is at fault. The exact JSON key from the request body (camelCase), so the client maps it to the form input without a lookup table. Absent for whole-request failures (a quota reached, a conflict). |
| `requestId` | Only on 500. The server's request ID, also in the `X-Request-ID` header and on every log line of that request. Users quote it to support; support finds the cause in the logs. |
| Route-specific extras | Allowed when documented for that route and machine-readable: `suspended: true`, `pending: true`, `verificationRequired: true`, a capped list of blocking records (`workspaces: [{id, name}]`, at most 100), a CAPTCHA `challenge` object. Never free-form debug data. |

**Never** answer validation failures as a map of every invalid field. One `{error, field}` at a time keeps the contract trivial; the client validates the obvious rules itself first (see `ui-patterns`) so the server's answer is the backstop.

### The 500

```http
HTTP/1.1 500 Internal Server Error
X-Request-ID: req_7Hq2LmN0pQ4sTu
Content-Type: application/json

{"error": "Something went wrong. Please try again.", "requestId": "req_7Hq2LmN0pQ4sTu"}
```

- One helper produces it (e.g. `internalError(w, r, err)`): it logs `err` with the request ID and writes the generic body. Handlers never write a 500 by hand, so nobody can accidentally put `err.Error()` in it.
- Panics are caught by the recovery middleware and answered the same way.
- The request ID is generated by the server for every request (a prefix + random base62, e.g. `req_` + 14). **Never** trust an incoming `X-Request-ID`: a client could make its request look like someone else's in the logs.

### Unknown routes

`/api/*` paths with no route answer `404 {"error": "Not found."}` as JSON, never the web app's HTML shell. A known path with the wrong method answers `405` (with an `Allow` header listing the methods it does take). Operator-only routes reached without the operator key answer exactly like an unknown route (404), so their existence isn't advertised.

## The table

| Code | Use it for | Never for |
| - | - | - |
| 200 | `show`, `index`, `update` (with the updated record), named actions returning data | Creation (201) |
| 201 | `store`, and named actions that create something the caller receives (e.g. a new set of recovery codes) | Async work that hasn't happened yet (202) |
| 202 | Work happens after the response (a listener sends the email), or the answer must be identical whether or not something exists (password reset for any valid email, sign-up with an emailed code) | Anything already done |
| 204 | `destroy`, logout, idempotent cancels, checks whose only answer is "yes" | Anything with a body |
| 400 | The request can't be read: malformed JSON, not exactly one object, unknown field, wrong JSON type, body over the cap, unknown/repeated/malformed query parameter, an unknown filter token, a cursor that isn't one of this list's rows or no longer exists | A value that parses but breaks a rule (422) |
| 401 | Not authenticated: no session, expired or revoked session, wrong sign-in credentials, a multi-step sign-in whose challenge ended | A wrong *current* password while signed in (422) |
| 403 | Authenticated, the target is visible to you, but you may not: missing permission, bad Origin or CSRF token, acting on something addressed to another person (an invitation to another email), a suspended account, a blocked network | Hiding existence from non-members (404) |
| 404 | Not found, not yours, malformed ID, unknown route | Business-rule refusals |
| 405 | A known path with a method it doesn't take | |
| 409 | The input is valid but the current state forbids it: last owner would leave, a feature already on, a unique value already taken (where revealing that is acceptable), a pending step not ready yet | A malformed or out-of-range value (422) |
| 415 | POST, PATCH, or DELETE with a body, without `Content-Type: application/json` | |
| 422 | Parsed but invalid: a value breaks a rule (`field` set), a typed confirmation that doesn't match, a wrong current password or code (`field` set), a quota reached (no `field`) | Shape problems (400) |
| 429 | This caller (IP, account, user) exceeded a rate limit. `Retry-After: <seconds left in the window>` | Limits shared by everyone (503) |
| 500 | An unexpected failure on our side | Anything the client could fix |
| 503 | Database unavailable; a limit shared by everyone reached (global sign-ups, global resets); a feature switched off by configuration that the route depends on (mail off for password reset); readiness while the server drains. `Retry-After` where a retry makes sense | Per-caller limits (429) |

Two optional codes, only where the feature exists:

- **410 Gone:** a one-time code that is no longer live (expired, replaced, or its attempts used up), when the client must restart the flow rather than retype. If you don't need that distinction, use 422 on the code field.
- **428 Precondition Required:** a rate limit's challenge level wants a solved CAPTCHA: `{error, challenge: {provider, siteKey, action}}`; the client resends the same request with the token in a header. See `security-defaults`.

## Decision rules

### 400 vs 422

Ask "could I even read what they meant?". If not (bad JSON, unknown key, a string where a number belongs, `page=1e3`), it's 400: a client bug, shown generically. If yes, and a rule says no (name too long, unknown enum value, wrong current password), it's 422 with `field`: a user error, shown on the form.

### 401 vs 422 for passwords

401 means "your session is not valid". The client reacts by clearing local state and redirecting to sign-in. So:

- Wrong password on **sign-in** -> 401 (there's no session yet; the same 401 for an unknown email and a wrong password, so the answer doesn't reveal which emails are registered).
- Wrong **current** password while signed in (change password, delete account, confirm a sensitive action) -> 422 `field: "currentPassword"` (or `"password"`). A 401 here would sign the user out for a typo.

### 403 vs 404

Run the tenant/ownership check first. If the caller can't see the target at all, it's 404 with the same body as a missing record. Only once the target is visible (they're a member) does a missing permission become 403. Example, `DELETE /api/workspaces/wsp_A/projects/prj_X`:

| Caller | Answer |
| - | - |
| Not a member of `wsp_A` | 404 |
| Member of `wsp_A`, `prj_X` belongs to `wsp_B` (even one they're also in) | 404 |
| Member of `wsp_A`, `prj_X` is malformed (`prj_123`, `usr_...`) | 404, no query run |
| Viewer of `wsp_A` (no `project.destroy`) | 403 |
| Admin of `wsp_A` | 204 |

Subtle case: a member without permission asking for a sub-record that doesn't exist. Prefer checking permission before loading the sub-record (403), since the member already knows the tenant exists and learns nothing new. For member management, a target outside this tenant is 404 and a target whose role you can't assign is 403.

### 409 vs 422

422: the request is wrong in itself and will stay wrong ("role must be one of ..."). 409: the request would be fine but the stored state conflicts, and it could succeed after the state changes (another owner is appointed, MFA is turned off first). Example: removing the last owner is 409; giving someone the role `superuser` is 422.

Quotas ("A workspace can have up to 1,000 projects.") are 422 without `field`: a business rule the request breaks, not a permission problem (403) and not a time-window limit (429).

### 202 and enumeration safety

When the existence of an account or address must not leak, every valid request gets the same status, body and timing:

```http
POST /api/auth/password-reset   {"email": "ada@example.com"}
-> 202 (whether or not an account uses that email)
```

The work (looking up the account, sending the link) happens in a listener after the response ([events-and-listeners.md](events-and-listeners.md)). The same pattern covers sign-up with an emailed code: the inbox receives either a code or "you already have an account", and the API answers 202 either way.

Where revealing is accepted (sign-up without email verification), a taken email is 409 with a generic message, and a blocked address gets **the same** 409 so the block list isn't revealed.

### 429 vs 503

429 is "you, slow down": it carries `Retry-After` for the caller's own window. 503 is "everyone, slow down" or "we're degraded": a global limit, the database down, a required feature off, or the server shutting down. Clients show different messages ("try again in 3 minutes" vs "the service is busy").

### Idempotent deletes and cancels

`destroy` of an existing record: 204. `destroy` of a missing record: 404 (the client asked for a specific thing). Cancelling a singleton that may not exist (`DELETE /api/auth/email-change`, "cancel my pending request"): 204 either way, because the end state the caller asked for holds.

## Headers that travel with codes

| Header | When |
| - | - |
| `X-Request-ID` | Every response, including 404, 405 and 500 |
| `Retry-After` | 429 and 503 (integer seconds) |
| `Allow` | 405 |
| `Cache-Control: no-store` | Every API response (personal data must not sit in shared caches) |
| `Content-Disposition: attachment` | File downloads (data export) |
