# Secrets and encryption

> Status: Draft · Milestone: Alpha (M0) · Updated: 2026-10-29

Lewbox holds a lot of other people's secrets: every cluster's CA private key and AerolVM PAT, DNS and storage credentials, GitHub App private keys, agent API keys and subscription tokens, sandboxes' environment variables, webhook signing secrets. This plan covers how they're encrypted at rest, how the keys that encrypt them are managed and rotated, which values are encrypted and which only hashed, the signing keys, and how secrets are kept out of logs.

## Today

- **One key for everything.** Laravel's `encrypted` and `encrypted:json` casts under `APP_KEY` (AES-256-CBC with an HMAC-SHA256 MAC, a base64 JSON payload `{iv, value, mac, tag}`), on:
  - `credentials.value`: cluster secrets (PAT, gossip key, CA certificate and private key, credential key), DNS (Cloudflare token), object storage (bucket keys), GitHub App (private key, client secret, webhook secret).
  - `profile_credentials.secret`, `profile_telemetry.settings` and `headers`, `sandboxes.env`, `templates.env`, `webhook_endpoints.secret` and `previous_secret`, `cluster_installations.token`.
- **No rotation.** Laravel supports `APP_PREVIOUS_KEYS` for decryption, but nothing re-encrypts, and rotating `APP_KEY` also logs everyone out.
- **The gateway's key** `GATEWAY_PORT_LINK_KEY`: a base64 Ed25519 seed in the environment, the same on every replica. It signs both port links and agent upload tokens. Changing it breaks every running private-port proxy until its port is exposed again.
- **The shared service token** `LEWBOX_GATEWAY_TOKEN`: one value in both services, no overlap on rotation, so rotating causes `503 app_unavailable` between the two restarts.
- **Secrets inside sandboxes, by design**: agent credentials and a Git token are written into each sandbox so `claude`, `codex` and `git` work there.

## Goals

- Every secret at rest encrypted with authenticated encryption, bound to the row and column it belongs to.
- Keys that can rotate without downtime, and a way to re-encrypt everything under a new key in the background.
- A path to keeping the root key in a KMS, without changing anything else.
- Secrets that can't be logged by accident.
- Signing keys that rotate without breaking running proxies.

### Non-goals

- Encrypting conversations (planned, Later; they're stored unencrypted, as the docs say).
- Protecting secrets from a sandbox that's meant to have them: a sandbox's own credentials are in it by design. What we limit is *which* secrets each sandbox gets ([sandboxes/profile-setup](../sandboxes/profile-setup.md), [git/tokens](../git/tokens.md)).

## Design

### Envelope encryption

```
LEWBOX_SECRET_KEYS (root keys, "KEKs")          in config, or a KMS later
        │ wraps
        ▼
encryption_keys table (data keys, "DEKs")       wrapped DEKs in Postgres
        │ encrypts
        ▼
*_encrypted columns                             ciphertext in Postgres
```

- **Root keys (KEKs)** come from configuration: `LEWBOX_SECRET_KEYS=k2:BASE64,k1:BASE64`. Each is 32 random bytes with a short id. The **first** is primary.
- **Data keys (DEKs)** are 32 random bytes, generated by Lewbox, stored in `encryption_keys` wrapped (encrypted) by a root key: `(id, root_key_id, wrapped bytea, created_at, retired_at)`. One DEK is active at a time; a new one is made when the root key changes, and optionally every 90 days.
- **Values** are encrypted with the active DEK.

Why two levels: rotating a root key means re-wrapping a handful of DEKs, not re-encrypting millions of values. And moving the root key into a KMS later only changes how DEKs are unwrapped.

### Ciphertext format

```
version (1 byte, 0x01) ‖ dek id (4 bytes, big-endian) ‖ nonce (24 bytes) ‖ ciphertext+tag
```

- **XChaCha20-Poly1305** (`golang.org/x/crypto/chacha20poly1305`): 24-byte random nonces are safe to generate at random for any number of values; fast everywhere without AES-NI (some arm64 nodes, though only the control plane encrypts).
- **Associated data** binds the ciphertext to where it lives: `"<table>.<column>:<row public id or internal id>"`. Copying one profile's encrypted credential into another profile's row fails to decrypt. This means every encrypt and decrypt call names its location, which the typed helpers below enforce.
- Stored in `bytea` columns named `<name>_encrypted`.

### In Go

```go
package secrets

type String struct{ … }                 // a secret value in memory
func (s String) Reveal() string         // the only way to read it; grep-able
func (s String) LogValue() slog.Value   // "***" + last four
func (s String) MarshalJSON() ([]byte, error) // refuses: secrets never serialise by accident
func (s String) String() string         // "***"

type Box interface {                    // the keyring
    Seal(ctx, plaintext []byte, ad AD) ([]byte, error)
    Open(ctx, ciphertext []byte, ad AD) ([]byte, error)
}
type AD struct{ Table, Column, Row string }

// Typed helpers per kind of value, e.g.
func SealJSON[T any](ctx, box, v T, ad AD) ([]byte, error)
func OpenJSON[T any](ctx, box, b []byte, ad AD) (T, error)
```

API responses never include `secrets.String`; resources that hold secrets have separate types for what's shown (e.g. a credential's provider, `verified_at` and last four, never the secret).

### What is hashed, not encrypted

Values Lewbox only ever needs to *check*, never read back: SHA-256 with last four ([ids-and-keys](ids-and-keys.md#storage)).

Admin keys, profile keys, sandbox keys, node tokens, install tokens (also encrypted, above), setup link tokens, dashboard session tokens, login codes (SHA-256 of code + the login attempt's id, since a 6-digit code alone has little entropy; attempts are limited to 5).

### Rotation

**A root key** (e.g. it may have leaked, or yearly):

1. Generate a new one: `openssl rand -base64 32`.
2. Put it first in `LEWBOX_SECRET_KEYS`, keeping the old one after it: `k2:NEW,k1:OLD`. Roll the replicas.
3. On start, Lewbox sees the primary root key changed: it creates a new DEK under `k2`, and enqueues `secrets.rewrap`, which re-wraps every DEK still under `k1` with `k2`.
4. `lewbox admin secrets status` shows when nothing is under `k1`. Remove `k1` from the config.

**A data key** (e.g. a DEK may have leaked, or periodically):

1. `lewbox admin secrets rotate` makes a new active DEK and enqueues `secrets.reencrypt`, which walks every encrypted column in batches, decrypting with the old DEK and encrypting with the new one, in short transactions.
2. When no value uses the old DEK, it's marked `retired_at` and can be deleted.

Lewbox refuses to start if a value it holds names a DEK it doesn't have, or a DEK names a root key not in the config, and says which.

### KMS

Later (or alpha, if wanted): root keys in a KMS instead of config.

- `LEWBOX_SECRET_KEYS=awskms:arn:aws:kms:…`, `gcpkms:projects/…`, `vault:transit/keys/lewbox`.
- Only DEK wrap and unwrap call the KMS: a handful of calls at start and on rotation, not per value. DEKs are cached unwrapped in memory.
- The `Box` interface hides which.

### Signing keys

Ed25519 keys sign port links and agentd channel tokens ([ids-and-keys](ids-and-keys.md#signed-tokens)).

- Stored in `signing_keys`: `(kid, purpose, public_key, private_key_encrypted, created_at, retire_after, retired_at)`. One active key per purpose (`port_link`, `agent_upload`). Separate purposes, so one leaking doesn't let anyone forge the other.
- Generated by Lewbox on first start: no setting needed. (Legacy's `GATEWAY_PORT_LINK_KEY` had to be set by hand, and private ports and agents were off without it.)
- `LEWBOX_SIGNING_KEYS` can override with configured keys, for operators who want them outside the database.
- **Rotation without breaking proxies:**
  - A new key is generated every 90 days (or `lewbox admin signing rotate`). The old one stays valid for verification until `retire_after` (default: 30 days later).
  - portd is started with *every* non-retired public key for `port_link` (`LEWBOX_PORTD_KEYS`, kid → key), so links signed by the new key work in old proxies started after it was made. A proxy started before a rotation knows only older keys; Lewbox signs links with the newest key *that sandbox's proxy knows*, which it records when it starts the proxy. Proxies are restarted with the new key set when their sandbox next starts.
  - Agent channel tokens are verified by the control plane, which knows every key, so rotation is immediate.

### Replacing APP_KEY

Legacy data is encrypted under Laravel's format and `APP_KEY`. The migration reads it with a small decrypter for Laravel's format (`base64(json{iv, value, mac, tag})`, AES-256-CBC, HMAC-SHA256 over `iv ‖ value`, verified before decrypting), given the legacy `APP_KEY` (and any `APP_PREVIOUS_KEYS`), and re-encrypts under the new keyring with the right associated data. It lives in the migration tooling, not the server ([migration](../migration.md)).

### Secrets in memory, logs and errors

- `secrets.String` everywhere a secret is held; `Reveal()` only where it's used (an HTTP header, a file written into a sandbox).
- A `slog` handler wraps every logger: values of type `secrets.String` are already redacted; as a backstop, string values matching token patterns (`lb[apsnil]_[0-9a-f]{64}`, `ghp_…`, `ghs_…`, `sk-ant-…`, `sk-…`, `Bearer …`) are replaced.
- Errors from external systems that may echo secrets (git's output with a token in a URL, AerolVM errors with a command line) go through `redact.Error` before being wrapped, logged, shown in activity (stderr tails, "with tokens and passwords taken out", as the docs promise) or stored.
- Commands run in sandboxes with secrets pass them by environment or by file, never on the command line, which `ps` and activity would show.
- Go can't reliably zero memory; we don't pretend to. Secrets live only as long as the request or job needs them.

## Security

- **Threat: a database dump leaks.** Without the root keys, encrypted values are useless, and tokens are hashes of 256-bit randoms. With the root keys too, everything is exposed: keep them apart (different backups, KMS).
- **Threat: an encrypted value is moved between rows** (e.g. by SQL injection or a bug). Associated data makes it fail to decrypt.
- **Threat: a root key leaks.** Rotate it: re-wrapping DEKs is quick. Then rotate DEKs too (re-encrypting values), since the old DEKs were exposed.
- **Threat: the signing key leaks.** Rotate; retire the leaked key immediately (`retire_after = now`), which breaks open port sessions until their proxies restart: acceptable in an incident. Restart affected sandboxes' proxies with a job.
- Random values only from `crypto/rand`.

## Observability

- `lewbox_secrets_operations_total{op,result}` (seal, open; ok, error). A decrypt failure is always an error log with the location (table, column, row), never the value.
- `lewbox admin secrets status`: values per DEK, DEKs per root key, signing keys and their state.
- Audit entries for rotation and for revealing a secret in the dashboard (if we ever allow it; we don't plan to).

## Configuration

| Setting | Default | |
|---|---|---|
| `LEWBOX_SECRET_KEYS` | Required | Root keys, `id:base64`, primary first |
| `LEWBOX_SIGNING_KEYS` | none (generated) | Override for Ed25519 signing keys |
| `LEWBOX_DEK_ROTATE_AFTER` | `2160h` (90 days) | Make a new DEK this often; `0` to only rotate by hand |
| `LEWBOX_SIGNING_ROTATE_AFTER` | `2160h` | |
| `LEWBOX_SIGNING_RETIRE_AFTER` | `720h` | How long an old signing key verifies after rotation |

`lewbox config check` refuses a root key that isn't 32 bytes, duplicate ids, or none at all, and prints how to make one.

## Testing

- Seal/open round trip; wrong associated data fails; tampered byte fails; unknown DEK fails with a clear error.
- Rotation: root key rotation re-wraps; DEK rotation re-encrypts every column in the registry (the test fails if a table has a `*_encrypted` column not in the re-encryption registry).
- Signing: rotation keeps old links valid until retirement; a proxy started with an older key set still accepts links Lewbox signs for it.
- Laravel decrypter: vectors produced by the legacy app (fixtures checked in).
- Redaction: secrets don't appear in logs, errors, JSON, activity, for every path that handles them (a test logs through each and greps the output).

## Build plan

1. `internal/secrets`: `String`, `Box`, XChaCha20-Poly1305 format, keyring from config, DEK table, typed helpers.
2. The column registry and `secrets.reencrypt` / `secrets.rewrap` jobs; `lewbox admin secrets`.
3. `internal/signing`: signing keys table, generation, rotation, verification sets.
4. The redacting `slog` handler and `redact.Error`.
5. The Laravel decrypter, with the migration tooling.
