# Dashboard: stack and structure

> Status: Draft · Milestone: Alpha (M0 scaffold, M4 complete) · Updated: 2026-10-29

How the React dashboard is built: its libraries, folder layout, API client, data fetching, live updates, authentication, routing, forms, errors, testing, and how it gets built into and served from the `lewbox` binary. Pages are described in their own plans ([dashboard](../dashboard.md#design)).

## Today

- `lewbox-legacy` builds Svelte 5 with Vite 8 / vite-plus (`vite.config.ts`, `svelte.config.js`, `package.json`, `pnpm-workspace.yaml`). Inertia renders pages with props from Laravel controllers. UI primitives are bits-ui wrapped in `resources/js/components/ui/**`, charts are layerchart, and terminals are xterm.js (`components/SandboxTerminal.svelte`).
- `lib/gateway.ts` (313 lines) is a small fetch client for the gateway with sandbox keys. `lib/conversation.ts` (430 lines) merges agent events into chunks. `lib/pagedList.svelte.ts` (160 lines) pages lists.
- `lewagent-legacy` is React 19 with Inertia, `@base-ui/react`, Tailwind 4, `lucide-react`, xterm.js 6, CodeMirror 6, Monaco, `react-markdown` with `remark-gfm`, highlight.js, `dockview-react` for panels, the React Compiler, and Vite 8 / vite-plus (`lewagent-legacy/package.json`). Its chat is `resources/js/lib/agents.ts` (1282 lines) and `components/chat-*.tsx`.

We match Lewagent's stack wherever it doesn't depend on Inertia, so components can move between the two.

## Goals

- A typed client generated from `api/openapi.yaml`, so a changed API breaks the dashboard's build, not its users.
- Data fetching with caching, deduplication, background refresh and optimistic updates, without hand-written stores.
- Live updates pushed from the server.
- Small, fast, cacheable: hashed assets with long cache lifetimes, code split by route.
- One command to develop: `lewbox serve` plus `vite` with hot reload, against a real or a fake backend.

### Folder layout

Plugins' UI lives beside their Go code, in `plugins/<name>/web/`, and is pulled into this build through the generated `web/src/plugins.gen.ts`; a workspace package, `web/packages/dashboard-plugin`, is the only part of the shell plugins import ([plugins/dashboard-slots](../plugins/dashboard-slots.md#how-plugins-reach-the-dashboard)).

```
web/
  index.html
  package.json
  vite.config.ts
  tsconfig.json
  src/
    main.tsx                    router, query client, providers
    api/
      schema.d.ts               generated by openapi-typescript (not edited)
      client.ts                 openapi-fetch instance: base URL, CSRF header, errors
      errors.ts                 ApiError: status, code, message, errors, requestId
      queries/                  query and mutation factories, one file per area
        sandboxes.ts            sandboxQueries.list(filters), .detail(id), useStopSandbox()…
        profiles.ts clusters.ts templates.ts webhooks.ts …
      events.ts                 the project event stream (see Live updates)
    routes/                     TanStack Router file routes (see navigation-and-layout)
    components/
      ui/                       Button, Badge, Dot, Dialog, Menu, Tabs, Field, Table, Callout,
                                Steps, Spinner, Empty, CopyButton, MiddleTruncate, Code, Time
      status/                   SandboxStatus, OperationProgress, NodeStatus, ClusterHealth,
                                BuildStatus, SessionStatus, ConversationStatus, DeliveryStatus
      terminal/                 Terminal (xterm), attach over WebSocket
      files/                    FileBrowser, FileEditor, UploadDropzone
      chat/                     the conversation UI (see sandbox-pages)
      charts/                   Chart, UptimeBar, Sparkline

    styles/app.css              Tailwind entry, theme tokens

```

### The API client

- `make api` (or `go generate ./api`) runs `openapi-typescript api/openapi.yaml -o web/src/api/schema.d.ts`. CI fails if the generated file differs from the committed one ([api/openapi-and-codegen](../api/openapi-and-codegen.md)).
- `client.ts` builds one `openapi-fetch` client with:
  - `baseUrl: '/v0'` (same origin), `credentials: 'same-origin'`;
  - an `X-CSRF-Token` header on every non-`GET` request, read from the `GET /v0/session` response and kept in memory;
  - a middleware that turns any non-2xx response into an `ApiError` with the API's `code`, `message`, `errors` and the `Lewbox-Request-Id` header, so every error the UI shows can carry the request id;
  - `Idempotency-Key: crypto.randomUUID()` on creates, held for the life of the form so a double submit or retry doesn't create twice.
- **Queries** are defined once per resource, as factories:

  ```ts
  export const sandboxQueries = {
    all: (prj: string) => ['projects', prj, 'sandboxes'] as const,
    list: (prj: string, f: SandboxFilters) =>
      infiniteQueryOptions({
        queryKey: [...sandboxQueries.all(prj), 'list', f],
        queryFn: ({ pageParam }) => api.GET('/v0/projects/{prj}/sandboxes', { params: { path: { prj }, query: { ...f, cursor: pageParam } } }),
        getNextPageParam: (page) => page.links.next ? cursorOf(page.links.next) : undefined,
      }),
    detail: (prj: string, sbx: string) =>
      queryOptions({ queryKey: [...sandboxQueries.all(prj), sbx], queryFn: … }),
  };
  ```

  (Paths here assume the Admin API lives at `/v0/projects/{prj}/…`, as [api](../api.md) proposes; the generated types follow whatever it decides.)
- **Cursor pages** use infinite queries, with "Load more" at the end of a table rather than numbered pages, since the API's cursors don't give totals ([api/conventions](../api/conventions.md)).
- **Mutations** invalidate the queries they affect, and do optimistic updates where it's safe: renaming, metadata edits, toggling a webhook endpoint. Lifecycle changes (stop, start, delete) aren't optimistic; they show the operation the API returns.
- **Operations** are followed through live events, not by polling, with a fallback poll of the operation (1 s, backing off to 5 s, as [sandboxes/operations](../sandboxes/operations.md) says) only when the event stream is down.

### Live updates

The legacy dashboard polls. The new one listens.

- **One stream per tab:** `GET /v0/projects/{prj}/events` (server-sent events), opened by `api/events.ts` when a project route mounts and closed when it unmounts. Each event is small, says what changed, and carries the new state where it's small enough:

  ```
  id: 18234
  event: sandbox.updated
  data: {"id":"sbx_…","status":"stopping","operation":{"id":"op_…","kind":"stop","step":"stopped"}}
  ```

- **What it carries:** sandbox status and operation steps, build status, node status and heartbeats, installation progress, session ends, port changes, conversation status (idle, running, waiting), webhook delivery results, sign-in progress, and new activity. It's the same set of facts that feeds webhooks and the activity log ([activity-and-webhooks](../activity-and-webhooks.md)), filtered to what the session's user may see.
- **What the dashboard does with an event:** `queryClient.setQueryData` for the resource when the event carries its new state, and `invalidateQueries` for lists it may move in or out of. Each area registers its handlers in its `queries/*.ts` file.
- **Reconnects** resume with `Last-Event-ID` (same origin, so the header works, unlike Lewagent's cross-origin `?after=`). If the server can't replay that far back, it sends `event: reset`, and the dashboard invalidates every query for the project.
- **Several tabs** each hold their own stream. A `BroadcastChannel` leader election, so one tab streams for all, is a later optimisation if replicas feel the connection count.
- **Streams that aren't project-wide** keep their own endpoints: a turn's events ([agents/turns-and-events](../agents/turns-and-events.md)), a command's output, a session's attach WebSocket, a build's log.
- **Fallback:** if the stream fails three times in a row, queries fall back to `refetchInterval` (10 s on detail pages, 30 s on lists) and a small banner says live updates are paused.

### Authentication

- **Sign-in** is by emailed code ([projects/users-and-login](../projects/users-and-login.md)). The API sets the session cookie: `__Host-lewbox_session`, `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`.
- **CSRF:** `GET /v0/session` returns the user, their projects, and a CSRF token tied to the session. Every state-changing request sends it as `X-CSRF-Token`. The API refuses a cookie-authenticated `POST`, `PUT`, `PATCH` or `DELETE` without it (`403`, `csrf_failed`). Bearer-key requests don't need it.
- **Inside a sandbox with a session.** Legacy minted a sandbox key for the dashboard and sent it to the gateway. In one binary, the dashboard can call inside-a-sandbox endpoints (commands, sessions, files, ports, conversations) with its session, as a project member acting on the project's sandbox. The API's permission check treats a member like an admin key, by their role ([projects/members-and-roles](../projects/members-and-roles.md)). This removes sandbox-key renewal from the dashboard entirely.
  - WebSockets (terminal attach) authenticate by the cookie on the upgrade request, plus a one-time `ticket` query parameter from `POST …/sessions/{ses}/tickets`. That way a cross-site page can't open the socket just because the cookie is there.
- **Session expiry:** a `401` from any request sends the user to `/sign-in?next=…`, keeping the path they were on. Forms in progress aren't lost: the dialog stays open, and signing in again in another tab lets the retry go through.
- **Project switching** doesn't change the session; the project is in the URL.

### Routing

- TanStack Router with file-based routes under `src/routes/`, generated route tree, and typed `Link`s. The tree is in [navigation-and-layout](navigation-and-layout.md#route-tree).
- **Loaders prefetch** a route's queries (`queryClient.ensureQueryData`) so pages render with data, and show the previous page until the new one is ready, with a top progress bar after 150 ms.
- **Search params are state:** list filters, cursors, selected tab and a file browser's path live in the URL, validated with a schema per route, so every view can be linked to and survives a reload.
- **Code splitting** by route: the terminal, the chat, CodeMirror and charts load only on the routes that use them.

### Forms

- One `Form` and `Field` pattern. A `422` `validation_failed` maps `errors` onto fields by name, including nested names (`repositories.0.ref`). Any other error shows as a callout above the submit button, with the request id.
- Client-side checks repeat the cheap rules (required, lengths, patterns from the OpenAPI schema), but the server is the authority.
- Dialogs for small creates (expose a port, add an SSH key, a webhook endpoint); full pages for large ones (a cluster, a template, a profile).
- A secret shown once (a key, a webhook secret, an install command with its token) appears in a `SecretReveal` that copies on click and warns before the dialog closes.

### Errors and empty states

- An error boundary per route shows what went wrong, the request id, and Retry. A `404` shows "not found or not yours", matching the API, which doesn't tell the two apart.
- Every list has an empty state that says what the thing is and how to make the first one, with a link to the docs.
- Toasts confirm background actions (key revoked, webhook test sent) and offer Undo where the API allows it.

### Theming and accessibility

- Light and dark, following the system, with a toggle saved in `localStorage`. Colours are CSS variables in `styles/app.css` that Tailwind's theme reads.
- Status colours are consistent everywhere: running green, transitional (creating, starting, stopping, deleting, building, pending) blue with a pulse, stopped grey, failed red, waiting amber.
- Every interactive element is reachable by keyboard; Base UI handles focus in overlays. Pages are checked with `axe` in the end-to-end tests.
- Keyboard shortcuts, listed with `?`: `⌘K` command palette, `g s` sandboxes, `g p` profiles, `g c` clusters, `g t` templates, `/` focus search.

### Shared components

The chat, terminal, file browser, status badges and the event-merging code are useful beyond the dashboard; Lewagent has its own versions of all of them today.

- They live in `web/src/components/{chat,terminal,files,status}` and depend only on props and callbacks, not on the dashboard's router or query client.
- At M4 we decide whether to publish them as `@lewbox/react` from this repository ([open question](#open-questions)). The event-merging code (`mergeEvent`, which both `lewbox-legacy/resources/js/lib/conversation.ts` and `lewagent-legacy/resources/js/lib/agents.ts` implement) moves into the TypeScript SDK either way ([sdks-and-cli/typescript](../sdks-and-cli/typescript.md#conversations)).

### Building and embedding

- `pnpm --dir web build` writes `web/dist/` with hashed assets.
- `web/embed.go`:

  ```go
  package web

  import "embed"

  //go:embed all:dist
  var Dist embed.FS
  ```

- `lewbox serve` serves the dashboard at `/`:
  - `/assets/*` from `Dist`, with `Cache-Control: public, max-age=31536000, immutable`, and precompressed `.br` and `.gz` when the build makes them;
  - any other `GET` that isn't an API, node, webhook or port-link path, and that accepts `text/html`, gets `index.html` with `Cache-Control: no-cache` and the Content Security Policy, so client-side routes work on reload;
  - `index.html` gets a small inline config (`<script type="application/json" id="lewbox-config">`) with the instance's name, logo URL and version. JSON isn't executed, so the CSP's no-inline-script rule holds.
- **The release build** runs `pnpm build` before `go build` ([foundation/build-and-release](../foundation/build-and-release.md)). A Go build without a built dashboard embeds a placeholder `index.html` that says how to build it, so backend contributors don't need Node.
- `lewbox serve --dashboard=false` turns the dashboard off, for API-only deployments.

### Development workflow

- `make dev` runs `lewbox serve --dev` (Go, restarted by `air` or `watchexec`) and `pnpm --dir web dev` (Vite on `:5173`) together.
- Vite proxies `/v0`, `/node`, `/setup-api` and WebSocket upgrades to `lewbox serve` on `:8080`, so the browser sees one origin and cookies work. `--dev` relaxes the CSP for Vite's hot reload and allows `http://localhost`.
- `lewbox serve --dev --fake-cluster` starts the [fake AerolVM cluster and toolbox](../foundation/testing.md) in-process, with a seeded project, profile, cluster and a few sandboxes. You can build every page without a real node.
- Storybook isn't planned; `web/src/routes/_dev/components.tsx`, only in dev builds, renders every UI component in its states.

## Testing

- **Unit (Vitest):** query factories, event handlers that patch the cache, the error mapper, `mergeEvent`, formatters.
- **Component (Testing Library with MSW):** forms map `422`s onto fields; status components for every status; the chat renders every chunk kind; the file browser's upload and rename.
- **End-to-end (Playwright):** against `lewbox serve --fake-cluster` with a fresh Postgres per run. Covers sign in → create project → add a cluster (fake) → create a profile and key → create a sandbox → run a command in the terminal → upload a file → expose a port → start a conversation with the fake ACP adapter → answer an approval → stop and start the sandbox, watching it update live without a reload. Plus the setup pages, from a setup link to Done.
- **Accessibility:** `@axe-core/playwright` on every page in the end-to-end run; no serious violations allowed.
- **Visual:** Playwright screenshots of key pages in light and dark, compared on change, kept as artifacts.
- **Bundle size budget:** the shell (sign-in plus the project layout) under 200 KB gzipped; CI reports the size of every route chunk.

## Build plan

1. Scaffold `web/` (Vite, React, TS, Tailwind, Base UI, TanStack Router and Query), lint and test setup, `make dev`. (M0)
2. Generate the client from the spec; `client.ts`, `errors.ts`, CSRF, idempotency keys. (M0)
3. Embed in the binary; SPA fallback; CSP; cache headers; placeholder build. (M0)
4. The UI kit: `components/ui/*`, `status/*`, `forms/*`, theme tokens, light and dark. (M0 to M1)
5. `api/events.ts`: the project event stream, handlers, reset, fallback polling. (M1, once the server has the stream)
6. Terminal, file browser, CodeMirror wrappers. (M2)
7. Chat components and `mergeEvent` (from the SDK). (M3)
8. Playwright suite and CI; axe; visual snapshots; bundle budget. (M1 onwards)

## Open questions

1. **Publish shared components** as `@lewbox/react`, or copy them into Lewagent? (Proposed: publish, from `web/packages/react`, once the APIs settle after the alpha.)
2. **Keep vite-plus**, as both legacy apps use, or plain Vite with ESLint and Prettier?
3. **Charts:** Recharts or visx? We need a line chart with a few series (CPU, memory, disk, load), an uptime bar and sparklines. Nothing exotic.
4. **One event stream per tab, or shared** across tabs with `BroadcastChannel`? (Start with one per tab.)
5. **WebSocket ticket vs cookie-only** for the terminal: is the extra round trip worth it given `SameSite=Lax` already blocks cross-site upgrades in most browsers? (Proposed: yes; WebSocket upgrades aren't covered by CORS.)
